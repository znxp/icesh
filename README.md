#  Snapshot Utility

Python utility for . Snapshot API creation, polling, downloads, SHA256 verification, streaming JSON parsing, merge, dedupe, and duplicate reporting.

## Dependency

```powershell
pip install -r requirements.txt
```

`ijson` is required for streaming large JSON array snapshot files.

## Important credential note

Do not commit real API keys to `config/settings.json`. If an API key was ever pasted into a screenshot, chat, ticket, or repository, rotate it before use.

## Configuration

Edit `config/settings.json`:

```json
{
  "api": {
    "base_url": "https://api.threatstream.com/api/v1/snapshot/",
    "username": "your_user@example.com",
    "api_key": "REPLACE_WITH_NEW_API_KEY"
  },
  "snapshot": {
    "intel_version": 1,
    "custom_config": {
      "filter": "state=\"active\" AND confidence>=50 AND date_first>=2026-01-01T00:00:00",
      "whitelist": {"type": ["ip", "domain"]},
      "format": "json_v2",
      "chunk_size": "100MB",
      "use_org_whitelist": true
    }
  }
}
```

The POST body generated by `snapshot-create` is:

```json
{
  "intel_version": 1,
  "custom_config": {
    "filter": "...",
    "whitelist": {"type": ["ip", "domain"]},
    "format": "json_v2",
    "chunk_size": "100MB",
    "use_org_whitelist": true
  }
}
```

## Local merge test

```powershell
python main.py merge --fresh --input-dir downloads --output-dir output --config config/settings.json
```

Outputs are written to a run-specific folder:

```text
output/runs/run_<timestamp>/
  merged/
  duplicates/
  reports/
```

With the default `threatstream_id` dedupe mode, the bundled sample file is expected to produce:

```text
processed=6 unique=6 duplicates=0 errors=0
```

If you switch to `operational` dedupe mode, the same sample should produce:

```text
processed=6 unique=3 duplicates=3 errors=0
```

## End-to-end sync

```powershell
python main.py sync --fresh --download-dir downloads/raw --output-dir output --config config/settings.json
```

## Fresh and resume

Use `--fresh` to reset SQLite state for a clean run. It does **not** delete previous output folders. Instead, each run writes to a new run-specific directory under `output/runs/`. Use `--resume` only when continuing an interrupted run.


### Windows note for `--fresh`

`--fresh` resets the SQLite state database only. It does **not** delete `output/`, `logs/`, or `downloads/raw/` because Windows can lock those folders via Explorer, editors, antivirus, or indexing and raise `WinError 5: Access is denied`. Previous run outputs are preserved under `output/runs/`.

For `sync`, downloaded API files are written into a snapshot-specific subfolder such as `downloads/raw/snapshot_8555784/`, and the merge step processes only that subfolder. This avoids mixing stale raw downloads with the current run while still preserving existing raw data.


## Updated `--fresh` cleanup behavior

`--fresh` removes:

```text
state.db
```

`--fresh` preserves:

```text
config/
logs/
downloads/raw/
output/runs/
```

Each merge or sync creates a new folder such as:

```text
output/runs/run_20260623_091512_123456/
output/runs/run_20260623_091512_123456_snapshot_8555784/
```

## Dedupe modes

The current default is now ID-based dedupe:

```json
"dedupe": {
  "mode": "threatstream_id",
  "identifier_field": "id"
}
```

In this mode, two records are considered duplicates **only when the ThreatStream object ID matches**. This preserves feed-level and source-level intelligence where the same IOC value appears in multiple feeds as different ThreatStream objects.

Supported modes:

| Mode | Dedupe key | Use case |
|---|---|---|
| `threatstream_id` | `id` | Raw/canonical ingest, preserves feed-level intelligence |
| `operational` | `itype + value` | Clean SIEM/SOAR matching view |
| `feed_aware` | `itype + value + feed_id` | Feed-level analysis without collapsing feeds |
| `custom` | `key_fields` from config | User-defined dedupe logic |

Examples:

```json
"dedupe": {
  "mode": "operational"
}
```

```json
"dedupe": {
  "mode": "feed_aware"
}
```

```json
"dedupe": {
  "mode": "custom",
  "key_fields": ["itype", "value", "feed_id", "source"]
}
```

### Merge context behavior

For `threatstream_id`, `merge_duplicate_context` defaults to `false`, so the winning/latest object is kept as-is and stale tags/fields from older versions are not reintroduced.

For `operational`, `feed_aware`, and `custom`, context merging defaults to enabled, so duplicate tags and source/feed values can be merged into the winning record.

To override explicitly:

```json
"dedupe": {
  "mode": "threatstream_id",
  "merge_duplicate_context": false
}
```

## Local test expectations after ID-based dedupe change

The bundled sample file has six records with unique `id` values. With the default `threatstream_id` mode, the expected local merge result is now:

```text
processed=6 unique=6 duplicates=0 errors=0
```

To reproduce the older behavior where the same IOC value is collapsed, temporarily set:

```json
"dedupe": {
  "mode": "operational"
}
```

Then the sample produces:

```text
processed=6 unique=3 duplicates=3 errors=0
```
